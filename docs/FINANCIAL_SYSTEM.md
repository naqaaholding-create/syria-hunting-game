# النظام المالي — لعبة رحلة صيد

**الحالة:** تصميم أولي فقط، وليس نظامًا ماليًا حيًا. المرحلة الأولى محاكاة بلا أموال حقيقية.

## قرارات المنتج
- العملة المرجعية: USD.
- الأرصدة منفصلة: `free_game` (مجاني وغير قابل للسحب)، `purchased_game` (رصيد مشتَرى للاستخدام داخل اللعبة وخاضع لشروط الشراء والاسترداد)، `earnings_available` (مكافآت معتمدة يمكن إنفاقها أو طلب سحبها)، و`earnings_held` (مبلغ محجوز أثناء مراجعة السحب).
- صندوق مكافآت اللاعبين: 20% من الإيرادات المؤهلة للفترة، مجتمعًا، وليس 20% لكل لاعب.
- توزيع المكافآت: وفق نقاط المهام والأداء المؤهل بعد فحوص مكافحة الغش.
- السحب: مراجعة إدارية يدوية. لا يُعد الطلب مدفوعًا إلا بعد تأكيد مزود الدفع والتحقق من مرجع التحويل.
- SafePal خيار تكامل محتمل لاحقًا، وليس شرطًا في النسخة الأولى. لا تخزن العبارة السرية أو المفتاح الخاص في التطبيق أو GitHub.
- لا تُفعّل إيداعات أو سحوبات حقيقية قبل مراجعة قانونية وأمنية ومحاسبية واختيار مزود دفع يدعم البلدان المستهدفة.

## قواعد محاسبية وأمنية
1. تُحفظ المبالغ بوحدات السنت الصحيحة (integer cents): 12.50 USD = 1250؛ لا تستخدم floating point للأموال.
2. كل عملية مرحلة تُسجّل في دفتر أستاذ append-only؛ التصحيح بقيد عكسي جديد، لا بتعديل أو حذف القيد القديم.
3. يجب أن تتوازن القيود المحاسبية لكل معاملة (مجموع المدين = مجموع الدائن) وأن يتم ترحيلها داخل معاملة قاعدة بيانات واحدة.
4. كل طلب حساس يستخدم مفتاح idempotency فريدًا لمنع التكرار.
5. لا يُعتمد الشحن إلا بعد تحقق الخادم من إشعار مزود الدفع وتوقيعه؛ لا تثق بإشعار من العميل.
6. لا يتحول الرصيد المجاني أو رصيد الشحن تلقائيًا إلى أرباح قابلة للسحب.
7. إنشاء طلب السحب يحجز المبلغ ذريًا؛ لا يمكن إنفاق المبلغ المحجوز أو طلب سحبه مرة ثانية.
8. تُراجع مكافآت المهمات من الخادم، مع حدود للمكافأة وفحوص التكرار والغش. لا يقبل النظام نقاطًا يرسلها العميل وحده.
9. لا يجوز للمدير الموافقة على طلب سحب أنشأه لنفسه. سجّل هوية المدير وسبب القرار، ويفضل اعتماد شخص ثانٍ للمدفوعات الكبيرة.
10. تُحمى بيانات وجهة الدفع بالتشفير وإدارة أسرار خارج المستودع، ولا تُسجّل بيانات دفع حساسة في السجلات.
11. تُعرّف الإيرادات المؤهلة كتابةً قبل الإطلاق: هل تخصم الاستردادات ورسوم المتاجر والضرائب والاحتيال؟ يجب توثيق نسخة القاعدة وتاريخ اعتمادها.
12. احتفظ بسجل تدقيق للقرارات الإدارية وتغييرات الأسعار وقواعد التوزيع؛ لا تسمح للواجهة الأمامية بالكتابة المباشرة إلى قاعدة البيانات.

## معادلة صندوق المكافآت
`player_pool_cents = floor(eligible_revenue_cents * 2000 / 10000)`

نقاط اللاعب المحتسبة هي مجموع نقاط المهام المقبولة في الفترة فقط. التوزيع المبدئي:
`player_reward = floor(pool_cents * player_eligible_points / total_eligible_points)`

تُعالج فروق التقريب بالسنت المتبقي وفق قاعدة معلنة وثابتة (مثل أكبر البواقي). إذا كان مجموع النقاط صفرًا، لا يُوزّع الصندوق تلقائيًا؛ تبقى الفترة للمراجعة وتُعالج حسب الشروط المنشورة. تُمنع النقاط المرفوضة أو قيد المراجعة من التوزيع.

## دورة طلب السحب
`requested -> under_review -> approved -> processing -> paid`
حالات بديلة: `rejected`, `cancelled`, `failed`.

- عند `requested`: تحقق من الرصيد المتاح واحجز المبلغ في معاملة ذرية.
- عند `approved`: خزّن المدير والمبرر والتوقيت.
- عند `processing`: سجّل مزود الدفع ومعرّف التحويل، دون كشف أسرار.
- عند `paid`: لا تنتقل إلى هذه الحالة إلا بعد تأكيد موثوق.
- عند الرفض أو الإلغاء قبل الدفع: أعد المبلغ المحجوز إلى الأرباح المتاحة بقيد عكسي موثق.
- لا تُنفّذ تحويلات فعلية من نسخة تجريبية أو من خلال مفاتيح موجودة في GitHub.

## الجداول المطلوبة
- `users`: حساب اللاعب وحالته.
- `wallet_accounts`: حسابات منفصلة حسب النوع والعملة.
- `ledger_transactions` و`ledger_entries`: دفتر الأستاذ ذي القيد المزدوج.
- `mission_performance`: نتائج المهمات المقبولة وفحوص النزاهة.
- `revenue_periods`: الفترة وتعريف الإيراد المؤهل والنسبة والموافقة.
- `reward_allocations`: نقاط ومكافآت كل لاعب لكل فترة.
- `shop_orders`: طلبات المتجر وأسعار المنتجات وقت الشراء.
- `payment_events`: إشعارات مزود الدفع ومعرّفاتها وحالة التحقق، دون بيانات بطاقة.
- `withdrawal_requests`: الطلب والمبلغ والحالة ووجهة دفع محمية.
- `admin_audit_log`: الفاعل والإجراء والسبب والتوقيت ومعرّف العملية.

## لوحة الإدارة
1. ملخص الإيرادات المؤهلة، الاستردادات، الرسوم، صندوق اللاعبين، والمبالغ المدفوعة/قيد الانتظار.
2. سجل قابل للتصفية لكل عملية مالية، مع رابط إلى قيود دفتر الأستاذ.
3. إدارة أسعار المتجر ومكافآت المهمات مع سجل تغييرات.
4. قائمة السحوبات ومراجعتها يدويًا مع أسباب القرار.
5. تنبيهات للتكرار، الشحنات غير المؤكدة، تضارب الرصيد، والنشاط غير المعتاد.
6. تصدير تقارير محاسبية دون تضمين معلومات دفع حساسة.

## مراحل التنفيذ
1. نسخة تجريبية: بيانات اختبار فقط، لا مزود دفع ولا سحب فعلي.
2. خادم موثوق وقاعدة بيانات وترحيلات واختبارات توازن الدفتر والتزامن.
3. اختبارات مكافحة الغش، استرداد الشراء، تكرار إشعارات الدفع، وطلبات السحب المتزامنة.
4. مراجعة قانونية وخصوصية وضرائب ومتطلبات متاجر التطبيقات ومزود الدفع في البلدان المستهدفة.
5. تفعيل الدفع الحقيقي تدريجيًا بعد الموافقات والاختبارات.

**تنبيه:** رصيد USD داخل قاعدة البيانات لا يعني وجود أموال فعلية. هذا الملف مواصفة تطوير، وليس استشارة قانونية أو ضمانًا لإمكانية تشغيل برنامج مكافآت نقدية.
